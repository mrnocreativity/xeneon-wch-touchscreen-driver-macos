# Verify touchscreen compatibility

1. Read the GitHub issue and any attached app-generated report. Record the exact retail model or listing, the macOS display name, the numeric display vendor and model IDs, the USB controller VID:PID, and the reported macOS driver results. The app offers the report after the pairing target accepts a physical touch. Its generated pairing line describes that test on one unit. Record gestures and reconnect behavior only when someone tested them.
2. For every new model report, check the [LinuxHW EDID archive](https://github.com/linuxhw/EDID) for the exact display. Start with the [digital display index](https://raw.githubusercontent.com/linuxhw/EDID/master/DigitalDisplay.md). Search for the retail model, the macOS display name, and, if both numeric IDs are available, the archive's manufacturer and product code. Download the index and search it locally if the browser truncates it. Open the candidate capture itself and verify that it can be tied to the exact retail model or hardware variant. If the index search is inconclusive and the manufacturer code is known, check the decoded captures under that manufacturer for the display name. Cite the capture, or record what you searched and which ID remains unverified.
3. Compare IDs in the same format. The app reports decimal values. Archive identifiers such as `ADI217A` combine a three-letter EDID manufacturer code and a four-digit hexadecimal product code. The numeric vendor ID packs the letters as `A = 1` through `Z = 26`, using `(first << 10) | (second << 5) | third`. Convert the hexadecimal suffix to decimal (`0x217A` is `8570`) and check it against the product field in the capture and the app report. Similar names, resolution, size, or a shared USB controller ID are clues for finding a capture. Only attribute its IDs to the reported model when the model or variant can be identified. If another source gives different IDs, document both and check for hardware revisions before choosing a match.
4. Check manufacturer listings and independent hardware reports for the exact retail model when more context is needed. A listing can corroborate the retail identity. A USB capture can corroborate the touch controller or report format. An EDID capture corroborates the display IDs. To independently verify macOS touch behavior, look for a second test with this driver on the same display identity or a maintainer's hardware test. Record the evidence for each claim with direct links.

Use the evidence levels in [Known Compatibility](../../../README.md#known-compatibility). A successful app-generated report supports a community-reported working entry for the tested unit. A hardware match alone supports candidate status. Before recommending built-in matching in [SupportedDisplayCatalog.swift](../../../Sources/MacXeneonEdgeTouchDriverCore/Display/SupportedDisplayCatalog.swift), check both display IDs and look for a second successful report with the same IDs or a maintainer test. If identity or behavior remains uncertain, say what evidence would resolve it. Follow the repository's authorization rules for code changes and GitHub actions.

The Logicom Nomad Touch is an example of partial verification. A [fork user reported it working](https://github.com/mrnocreativity/xeneon-wch-touchscreen-driver-macos/issues/1), and an [independent owner report](https://github.com/linuxwacom/wacom-hid-descriptors/issues/596#issuecomment-5875879272) identifies the WCH `27C0:0859` controller and the EDID name `NOMAD_TOUCH` with manufacturer code `APT`. The numeric product ID is missing from that report. The issue also contains an EDID for a different model, so check which device each comment describes.
