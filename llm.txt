# Xeneon WCH Touchscreen Driver for macOS: AI Installation Runbook

Use this file when a user asks a local coding agent to install, verify,
troubleshoot, or remove this repository's driver. The agent must have access to
the checked-out repository and a terminal on the Mac that will use the
touchscreen.

## Intended result

Install the current release build for the current macOS user, register its
LaunchAgent, help the user complete macOS privacy approval and physical display
pairing, and verify actual touchscreen behavior. A successful build alone is
not a successful installation.

The driver targets macOS 13 or newer and touch controllers reporting:

- product name: `wch.cn TouchScreen`
- USB VID:PID: `27C0:0859`

Known displays and the limits of current compatibility evidence are documented
in `README.md`.

## Authority and safety boundaries

When the user explicitly asks you to install this repository, you may run the
read-only preflight checks below without asking for another confirmation. If
the checks find no warning condition, you may then run `./Scripts/install.sh`.
If a check proves that required software is unavailable, the code does not pass
its local checks, or the required controller is not currently attached, inform
the user and ask whether to continue before running the installer.

- Do not use `sudo`; the installer is intentionally per-user.
- Do not disable macOS security features or attempt to bypass privacy approval.
- Do not delete or replace existing configuration or pairings during a routine
  installation.
- Do not print, paste, commit, or report hardware serial numbers, USB location
  IDs, usernames, signing identities, or other machine-specific identifiers.
- Do not change gesture or display configuration unless diagnosis proves it is
  necessary and the user approves the specific change.
- Do not commit, push, publish, open a pull request, or alter an existing pull
  request unless the user separately requests it.
- Do not uninstall or remove privacy entries unless the user explicitly asks.
- Preserve unrelated worktree changes.

Input Monitoring, Accessibility, and each **Touch this display** calibration
touch require the user. Explain the exact step, wait for confirmation, and then
continue. Never claim to have completed a physical or System Settings action
that the user performed.

## Stable internal installation identity

Generated files intentionally use the original reverse-domain identifier
`com.ajvwhite.MacXeneonEdgeTouchDriver`, even in the
`mrnocreativity/xeneon-wch-touchscreen-driver-macos` fork. This is the stable
internal identity inherited from the original project. It keeps upgrades on
the same LaunchAgent, executable location, configuration, logs, saved pairings,
and macOS privacy identity.

The name does not represent a dependency, network service, extra application,
or unexpected third-party installation. Replacing it with a fork-specific name
such as `com.nocreativity` would create a second installation identity, could
leave duplicate LaunchAgents, and could make macOS request privacy approval
again.

## 1. Read-only preflight

Start in the repository root. Confirm the repository and tooling before making
changes:

```sh
test -f Package.swift
test -x Scripts/install.sh
test "$(uname -s)" = "Darwin"
sw_vers -productVersion
command -v swift
swift --version
sh -n Scripts/install.sh Scripts/uninstall.sh Scripts/build-release.sh
git status --short --branch
```

Confirm that the installed macOS major version satisfies the package's macOS 13
minimum:

```sh
macos_version="$(sw_vers -productVersion)"
macos_major="${macos_version%%.*}"
test "$macos_major" -ge 13
```

Run the package's basic code checks before deciding that installation is likely
to work on this Mac:

```sh
swift test -Xswiftc -warnings-as-errors
swift build -c release -Xswiftc -warnings-as-errors
```

Check whether the exact USB controller matched by the production driver is
currently attached. This command prints only the presence result, not device
serial numbers or USB location IDs:

```sh
ioreg -p IOUSB -l -w0 -r -c IOUSBHostDevice | awk '
  BEGIN { RS="" }
  /"idVendor" = 10176/ && /"idProduct" = 2137/ { found=1 }
  END {
    if (found) {
      print "Required USB controller 27C0:0859 detected"
      exit 0
    }
    print "Required USB controller 27C0:0859 not detected"
    exit 1
  }
'
```

The decimal values above are USB vendor `0x27C0` and product `0x0859`, the
constants used by `XeneonEdgeDevice` and `HIDDeviceMonitor`. A successful check
proves only that the required controller is present. It does not prove every
gesture will work, and it does not identify compatibility from a retail brand
or product name.

Check whether the LaunchAgent is already registered. A nonzero result is normal
before the first installation:

```sh
launchctl print "gui/$(id -u)/com.ajvwhite.MacXeneonEdgeTouchDriver" >/dev/null 2>&1 || true
```

Note whether these existing files are present, but do not remove or print their
contents:

```text
~/Library/Application Support/MacXeneonEdgeTouchDriver/config.json
~/Library/Application Support/MacXeneonEdgeTouchDriver/pairings.json
~/Library/LaunchAgents/com.ajvwhite.MacXeneonEdgeTouchDriver.plist
```

The installer preserves an existing config. Existing pairings may remain valid
when the attached devices expose sufficiently unique public identities; some
identical panels intentionally require physical pairing again after reboot.

## 2. Decide whether installation is currently useful

Base this decision only on the objective preflight results. Do not use the
README compatibility table, retail display name, crowdsourced reports, visual
similarity to a known display, or model intuition as a reason to warn or stop.

Continue directly when all of these are true:

- the host is macOS 13 or newer;
- Swift and the repository scripts are available;
- script syntax, tests, and the warning-clean release build pass;
- USB controller `27C0:0859` is currently detected.

Warn the user before installation when an objective check fails. The warning
must state the failed check, the practical consequence, the recommended next
action, and that the user may continue anyway.

Use these distinctions:

- **Required hardware not currently detected:** explain that the driver can be
  installed, but touch cannot work or be physically verified until a
  `27C0:0859` controller is connected. Do not call the display incompatible;
  it may simply be disconnected or intended for later use.
- **Software prerequisite unavailable:** identify the missing or unsupported
  prerequisite, such as macOS below version 13 or no Swift toolchain. Explain
  which installation or runtime step it prevents.
- **Code check failed:** report whether script syntax, tests, or the release
  build failed and summarize the relevant error without hiding it behind a
  compatibility guess.

Then ask whether the user wants to correct the issue first or continue anyway.
Do not run `./Scripts/install.sh` until the user answers. If the user chooses to
continue, proceed through every technically possible step and report expected
failures or unverified behavior truthfully. A missing tool may make a requested
command impossible; user permission to continue does not turn that failure into
success.

Unknown or unlisted hardware is not itself a warning condition. Only the exact
local evidence above triggers this pause.

## 3. Choose signing behavior

If the user has already supplied a stable `CODESIGN_IDENTITY`, preserve and use
it:

```sh
CODESIGN_IDENTITY="Developer ID Application: supplied identity" ./Scripts/install.sh
```

Do not invent an identity, reveal its value in your report, or ask the user to
paste private signing material into chat. If no identity was supplied, use the
normal installer command below. Its linker ad-hoc signature is supported, but
macOS may request new privacy approval when a rebuilt executable changes.

## 4. Install

Run from the repository root:

```sh
./Scripts/install.sh
```

Do not prefix this command with `sudo`. The script builds the release binary,
copies it to the current user's Application Support directory, creates the
LaunchAgent, preserves an existing config, and bootstraps the agent.

Expected installed locations:

```text
Binary:
~/Library/Application Support/MacXeneonEdgeTouchDriver/bin/MacXeneonEdgeTouchDriver

LaunchAgent:
~/Library/LaunchAgents/com.ajvwhite.MacXeneonEdgeTouchDriver.plist

Config:
~/Library/Application Support/MacXeneonEdgeTouchDriver/config.json

Logs:
~/Library/Logs/MacXeneonEdgeTouchDriver/
```

## 5. Hand macOS privacy approval to the user

Tell the user to open **System Settings > Privacy & Security** and grant:

- **Input Monitoring**
- **Accessibility**

Approval should apply to the installed driver binary, or to the launching app
if macOS attributes the request there. Use the exact installed binary path
printed by the installer when identifying it. The agent cannot click, script,
or bypass these approvals on the user's behalf.

Wait until the user confirms both approvals. Then restart the registered agent
so it receives the current permission state:

```sh
launchctl kickstart -k "gui/$(id -u)/com.ajvwhite.MacXeneonEdgeTouchDriver"
```

If macOS requires logout, login, or another manual confirmation, explain that
truthfully and wait rather than repeatedly changing the installation.

## 6. Hand physical pairing to the user

When **Touch this display** appears, tell the user to touch that message on the
physical touchscreen where it is displayed. Repeat once for every pairing
overlay. Do not click an overlay with computer-use automation or guess display
coordinates; the point of this step is to associate the USB controller that
reported the physical touch with the display showing the overlay.

Identical panels with duplicate or missing public serials may deliberately ask
for pairing once after each Mac reboot. This is a safety behavior, not an
installation failure.

## 7. Verify the installed service

Confirm that the registered LaunchAgent and installed binary are valid:

```sh
launchctl print "gui/$(id -u)/com.ajvwhite.MacXeneonEdgeTouchDriver"
codesign --verify --strict --verbose=2 \
  "$HOME/Library/Application Support/MacXeneonEdgeTouchDriver/bin/MacXeneonEdgeTouchDriver"
```

Inspect recent logs locally:

```sh
tail -n 100 "$HOME/Library/Logs/MacXeneonEdgeTouchDriver/driver.log"
tail -n 100 "$HOME/Library/Logs/MacXeneonEdgeTouchDriver/stderr.log"
```

Summarize relevant health, permission, controller-discovery, display-matching,
and pairing messages. Do not reproduce device fingerprints, serial numbers,
location IDs, usernames, or unrelated log content in chat.

If pairing was completed, confirm that `pairings.json` exists without printing
it:

```sh
test -f "$HOME/Library/Application Support/MacXeneonEdgeTouchDriver/pairings.json"
```

## 8. Verify user-facing behavior

Ask the user to test every connected touchscreen separately:

1. Single-tap a harmless control on that display.
2. Double-tap or double-click a harmless target.
3. Drag immediately to scroll.
4. Hold briefly, then move to drag a UI element.
5. Confirm that touching one display does not activate another display.

At least tapping and correct per-display targeting must be physically confirmed
before reporting the driver as working. Record any gesture or display that was
not tested as an explicit verification gap.

## Focused troubleshooting

- Driver exits immediately: inspect `driver.log` and verify Accessibility for
  the exact installed binary or attributed launcher.
- HID open failure: verify Input Monitoring and check whether another process
  has seized the same controller.
- Privacy approval disappears after rebuild: reinstall consistently with the
  same stable `CODESIGN_IDENTITY`, if the user has one, and approve that signed
  binary once.
- No compatible display is detected: use `swift run DisplayInfo` for local
  diagnosis, summarize only non-sensitive matching information, and do not
  change config without approval.
- Pairing overlay returns after reboot on identical displays: this is expected
  when public controller or display identities are ambiguous.
- Need deeper HID diagnosis: `swift run HIDDump` is non-seizing and separate
  from the production daemon, but use it only when ordinary logs are
  insufficient and avoid publishing raw identifiers.

Do not delete `pairings.json` as a generic repair. Reset it only when the user
specifically wants to discard display assignments and approves that action.

## Uninstall only when explicitly requested

```sh
./Scripts/uninstall.sh
```

This removes the LaunchAgent and Application Support installation while
keeping logs. macOS Privacy & Security entries must be removed manually if the
user no longer wants them remembered.

## Final report

Report:

- objective usefulness preflight: ready, warning accepted, or blocked, with the
  exact failed check when applicable;
- macOS and Swift prerequisites: passed or blocked;
- build and per-user installation: passed or blocked;
- LaunchAgent state and code-signature verification: passed or blocked;
- Input Monitoring and Accessibility: user-confirmed or still required;
- physical pairing for each display: user-confirmed or still required;
- single-tap and correct per-display targeting: user-confirmed or unverified;
- double-click, scrolling, and hold-drag: user-confirmed, failed, or unverified;
- relevant log errors and the next focused action.

Do not describe installation as complete while required privacy, pairing, or
physical behavior checks remain unverified.
